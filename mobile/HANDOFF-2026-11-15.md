## 下一处要定位的问题

不要先重复输入密码。原账号管理页查询的是 `getAccounts("com.google", "com.android.vending")`，空列表有多种含义：

1. `com/vlite/sdk/client/virtualservice/accounts/a.smali` 的 `S` 方法会把 Binder / 服务异常转为空数组。
2. `com/vlite/sdk/server/accounts/a.smali` 的 `V0` 先检查认证器和账号类型；`t` 从原缓存取候选；`x1` 只保留 visibility 1 / 2。
3. 同类 `Y` 若无法通过虚拟 PM 解析 `com.android.vending`，会返回 visibility 3，随后被筛除。即使候选存在且全为 3，也仍需区分缺包和其他不可见原因，不应直接放开可见性。
4. 管理页没有自己的 onResume / onActivityResult 刷新；已通过重新创建页面排除一次单纯旧列表。其“添加”按钮只启动 GMS LOGIN intent，不在此页面接收保存成功结果。
5. 账号保存链为 `accounts/m.addAccountExplicitly -> accounts/a.r0/O -> a.t0`。不要按普通 AOSP 猜测样本行为：本样本 `A0` 实际恒 true，不能把 user locked 模板文本当作当前原因。

拟定的 Privacy13 只对原 `com.google + com.android.vending` 查询增加固定事件 / 布尔 / 数量：客户端成功或异常、认证器存在与类型允许、候选数、visibility 各类计数和最终可见数。只需正常打开管理页即可触发，不需要先重新提交密码。不得输出账号标识、令牌、异常 message / stack 或完整认证 Intent；不得改变查询、权限、结果或原异常行为。计划仅修改 `classes4.dex`，复用 Privacy12 的全部屏蔽模块、兼容库、host helper、core 和预置 APK 字节。

另有一个 GMS unstable 后台进程的 SIGSEGV，仅保留 `libhoudini.so +0x358158 / +0x30e7cf` 两帧；它比纠正密码和条款步骤的时间下界早约 301 秒，没有证据将其归为账号为空的原因或此前 CriticalNative 嵌套问题。GMS 不在选定隐私策略包范围内，兼容模块和隐私策略应分别判断。不要为补充旧栈而重复登录。

登录路径一旦推进，必须确认回到**容器内 Claude 的已登录界面**。外层同版 Claude 仅作原版分包导入来源，未启动；其 `SecretLinkActivity` 也能接收回调，不能将外层打开或 Google 授权页面当作容器登录成功。验证需结合实际宿主 UID、代理任务和真实 Claude 进程身份，不记录认证 URL 参数或令牌，不手工重放回调。
